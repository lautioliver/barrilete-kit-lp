La tesis

Dos decisiones son siempre tuyas.

Punto de control 1

Aprobar el plan.

/plan-feature investiga el código y los ADRs, arma la épica con sus issues y bloqueos, y te la muestra. No escribe código hasta que digas que sí.

Punto de control 2

Mergear.

/implement-issue llega hasta el PR con tests en verde. /review-pr lo revisa en otra sesión. El merge lo hace una persona.

Las skills mejoran con el uso, pero no se reescriben solas: /improve-skills propone ajustes en un PR y nunca afloja controles.

El flujo

De la idea al merge, con la rienda en dos nudos.

  1. 01
    idea
    /plan-feature
    épica + issues con bloqueos
  2. Punto de control
    02
    aprobás el plan
    Sin tu sí, no hay código.
  3. 03
    implementa
    /implement-issue <n>
    tests en rojo desde los criterios, probados con un reporte JUnit o TAP, código hasta verde, autorevisión, docs
  4. 04
    PR
    /review-pr <n>
    en otra sesión, que vuelve a correr el rojo, más /security-review si toca rutas sensibles
  5. Punto de control
    05
    mergeás
    El merge lo hace una persona.
  6. 06
    retro
    en la rama agents/retros →
    /improve-skills
    propone ajustes en un PR

Si un issue depende de otro, queda con status:blocked. El workflow unblock.yml le saca el label solo cuando se cierran todos los bloqueantes.

Autonomía del agente

Qué puede hacer solo, qué tiene que consultar y qué nunca.

Barandas

.claude/settings.json + guardrails.py: hook que frena merge, tags, releases y push a ramas troncales.

Mapa para agentes

docs/agents-map.json dice qué docs revisar según lo que cambia y cuáles rutas son sensibles.

Docs testeados en CI

Links, rutas y ADRs rotos, rutas del mapa que ya no existen, shellcheck y los test-*.sh: si algo se rompe, falla el check.

Verificación antes del PR

verify.py corre lint, typecheck, tests afectados y drift de migraciones según lo que cambió.

Rojo verificado

red.sh acepta un rojo solo con un reporte JUnit o TAP: una aserción que falla en un test nuevo. Los crashes, los timeouts, los errores de carga y los tests viejos rotos no cuentan.

Pedíselo en el chat

Decís una frase. Pasa esto.

“abrí un issue: el QR no valida sin conexión, es urgente”
→ create-issue

Arma título y labels según la convención, busca duplicados, te muestra el borrador y lo crea cuando confirmás.

“la migración de pagos depende de que se cierre el issue 25”
→ create-issue

Registra el bloqueo nativo de GitHub (“Blocked by”) y pone status:blocked. unblock.yml lo saca al cerrarse los bloqueantes.

“planificá la migración de cuentas”
→ /plan-feature

Investiga el código y arma una épica con sub-issues y bloqueos, en el orden en que se pueden hacer.

“pasá esta auditoría a issues”
→ create-issue

Un issue por hallazgo, con el link al documento.

“¿qué puedo hacer ahora?”
→ /project-status

Lo libre por prioridad, lo bloqueado con su motivo y el avance de cada épica.

“sumá a @ana al equipo, cubre pagos”
→ /add-member

Valida usuario y áreas y lo agrega a .github/team.json. Los issues de pagos nacen asignados a quien tenga menos carga.

Skills

13 skills para todo el ciclo.

Viven en .claude/skills/. Las que empiezan con / se invocan como comando; las otras el agente las usa cuando hacen falta. Máximo 120 líneas cada una, controlado por check-docs.py.

/plan-feature
Investiga y convierte una idea en épica + issues. No escribe código.
create-issue
Issues sueltos, auditorías a issues, bloqueos entre issues.
/implement-issue <n>
Del issue al PR con TDD: red.sh comprueba que los tests fallen por una aserción, después código hasta verde. No mergea.
debug
Síntoma → evidencia → causa raíz → arreglo → test de regresión.
db-migration
Plan con compatibilidad, backfill y rollback antes de tocar el schema.
update-docs
Corrige los docs que quedaron viejos, en el mismo PR.
/review-pr <n>
Revisa reglas de negocio, ADRs, docs, tests y rutas sensibles. No aprueba.
/improve-skills
Junta retros y señales objetivas (fallas de CI, reverts) y propone ajustes en un PR. Nunca afloja controles.
/project-status
Versión, trabajo, épicas, PRs, deuda, decisiones y “¿qué puedo hacer ahora?”.
git-workflow
Ramas, commits y PRs.
/orchestrate
Reparte hasta 3 issues entre subagentes en paralelo, cada uno en su worktree, y junta PRs y consultas en un solo mensaje.
/add-member · /remove-member
Agregar, editar, pausar o quitar integrantes del equipo que recibe los issues.
Subagentes por modelo

Tres en paralelo. Ninguno mergea.

/orchestrate reparte hasta 3 issues disponibles: elige Haiku o Sonnet según routing.py y Opus revisa. Cada uno trabaja en su propio worktree y todos comparten el contrato de docs/agents/subagent-contract.md.

Sonnet
implementer

implement-issue en el worktree que le pasan: lógica de negocio, bugs, features y lo que escala el liviano.

Haiku
implementer-light

Issues chicos sin rutas sensibles ni lógica de negocio. Si encuentra algo de eso, frena y escala.

Opus
reviewer

review-pr desde otro contexto, en un worktree propio. No publica: devuelve los hallazgos.

PRs listos, consultas y escalados llegan juntos en un solo mensaje. Nada se mergea ni se publica sin tu confirmación.

Cómo aprenden

Mejoran con el uso. No se reescriben solas.

  1. 1
    Retro en cada corrida

    Cada implement-issue y review-pr deja una retro en la rama agents/retros. Solo git: no ensucia los PRs.

  2. 2
    Patrones, no anécdotas

    /improve-skills busca al menos dos casos (o uno grave) y prefiere convertirlos en scripts o checks antes que en más texto. Se puede programar semanal.

  3. 3
    Siempre en un PR

    Los ajustes llegan como PR. Lo que no alcanza para cambiar una skill va a docs/agents/lessons.md, que implement-issue lee antes de empezar.

Los agentes aprenden de lo consolidado y revisado, nunca de retros crudas. Dos checks del workflow de labels salieron de este circuito en un repo real: un PR con business-logic tiene que tocar docs/decisions/, y un PR que llega sin type: lo copia del issue que cierra.

Equipo y asignación

Cada issue nace con responsable.

.github/team.json lista a los integrantes: usuario de GitHub, nombre, áreas que cubren y si están activos o en pausa. Lo leen solo los scripts que crean issues: create-issue y planner.py.

01
Por área

Entre los activos, los que cubren alguna area: del issue.

02
Si nadie la cubre

Todos los activos.

03
Menos carga gana

El de menos issues abiertos asignados. En una épica, la carga se reparte entre los issues del mismo plan.

Asignado significa responsable.

No “lo está trabajando”. available.sh muestra primero lo tuyo, marca “en curso” lo que tiene PR abierto y separa lo mergeado que espera release. prepare.sh no deja tomar un issue de otra persona.

Para una o dos personas.

Rama base

El segundo argumento del init define a dónde van los PRs.

init-template.sh "X" main
rama → main

Proyecto nuevo, sin usuarios todavía.

init-template.sh "X" develop
rama → develop → main

Separar integración de producción.

init-template.sh "X" develop releases
rama → develop → release/vX.Y.Z → main

Ya hay usuarios: cada versión se congela y se prueba en staging.

¿El proyecto creció? python3 scripts/grow.py lo pasa al modo completo (con --releases si la base es develop y querés ese flujo). Lo que nunca tocaste se reemplaza; lo que modificaste queda intacto y la versión completa espera en .agent-kit/pending/. No commitea: revisás el diff y abrís un PR.

Ir al instalador

Usar la plantilla

  1. 1

    Creá el repo

    En GitHub: Use this template → Create a new repository, y cloná el repo nuevo.

    Use this template
  2. 2

    Inicializá

    bash 
    ./scripts/init-template.sh "Nombre del proyecto" main --lang es

    Para un proyecto chico (una o dos personas), agregá --small al final.

  3. 3

    Completá los TODO:

    bash 
    grep -rn "TODO:" .

    Lo más importante es docs/agents-map.json: rutas reales de schema, auth, pagos y API pública. El check de docs falla a propósito mientras queden rutas TODO/: con rutas de ejemplo, un agente nunca detectaría que tocó algo sensible.

  4. 4

    Cargá al equipo

    /add-member @usuario por cada integrante, con las áreas que cubre. Desde ahí, cada issue que creen los agentes nace asignado.

  5. 5

    Creá los labels

    Actions → Labels → Run workflow.

  6. 6

    ¿Usás Codex?

    Enlazá las skills: mkdir -p .agents && ln -s ../.claude/skills .agents/skills. Copilot y Cursor las leen de .claude/skills sin hacer nada. Qué funciona en cada herramienta.

Requisitos GitHub con sub-issues y dependencias de issues · agentes con push a agents/retros · gh autenticado · jq y python3

Sumar a un proyecto existente

¿Ya tenés un repo? El instalador suma el kit sin pisar tus archivos. Corrilo desde la raíz del proyecto, con el working tree limpio:

bash 
curl -fsSL https://raw.githubusercontent.com/lautioliver/barrilete-kit/main/scripts/install.py | python3 - "Proyecto" main --lang es

O cloná la plantilla y correlo desde el clon, para leerlo antes de correrlo:

bash 
git clone https://github.com/lautioliver/barrilete-kit /tmp/barrilete-kit
python3 /tmp/barrilete-kit/scripts/install.py "Proyecto" main --lang es

Opciones: --lang es deja la prosa en español, --small es el modo chico y --draft imprime el plan y no escribe nada. main es la rama base (o develop), y releases funciona igual que en el init. --template <url o ruta> y --version vX.Y.Z eligen de dónde sale el kit. Lo que va después de -- se pasa tal cual a init-template.sh (por ejemplo -- --lang es).

Glosario

Diccionario de a bordo.

Las palabras técnicas de esta página, en una línea cada una.

Agente de código
Un modelo de IA (Claude Code, Cursor) que lee, escribe y ejecuta código en tu repo.
Plantilla de repo
Un repo de GitHub que se copia como punto de partida para uno nuevo, con todos sus archivos.
AGENTS.md
El archivo con las reglas que el agente lee antes de trabajar. CLAUDE.md y llms.txt apuntan a él.
Skill
Una receta escrita que el agente sigue para una tarea concreta. Las que empiezan con / se invocan como comando.
ADR
Architecture Decision Record: un documento corto que registra una decisión técnica, por qué se tomó y qué se descartó.
Issue
Una tarea, bug o pedido registrado en GitHub, con sus criterios de aceptación.
Épica
Un issue grande que agrupa varios sub-issues de la misma funcionalidad.
Bloqueo
Una dependencia entre issues: uno no se puede empezar hasta que se cierre el otro.
PR
Pull request: el pedido para sumar los cambios de una rama a la principal, donde se revisan.
Merge
Aceptar un PR e integrar sus cambios a la rama principal.
Label
Una etiqueta en issues y PRs (type:, status:…) para clasificarlos y filtrarlos.
CI
Integración continua: checks automáticos que corren en cada PR y fallan si algo se rompió.
Workflow
Un archivo de GitHub Actions (.yml) que automatiza algo: correr tests, sincronizar labels, desbloquear issues.
TDD
Test-driven development: primero escribís el test que falla (rojo), después el código que lo hace pasar (verde).
JUnit y TAP
Dos formatos estándar en los que los runners de tests informan el resultado de cada caso. red.sh los lee en lugar de adivinar por la salida.
Lint y typecheck
Revisiones automáticas de estilo y de tipos que encuentran errores sin ejecutar el código.
Test de regresión
Un test que reproduce un bug ya arreglado, para que no vuelva a aparecer.
Migración y schema
El schema es la estructura de la base de datos; una migración es el cambio versionado que la modifica.
Backfill y rollback
Backfill: completar datos existentes tras un cambio de schema. Rollback: el camino para deshacerlo.
Rutas sensibles
Partes del código donde un error cuesta caro (auth, pagos, schema, API pública) y piden revisión extra.
Retro
Notas de qué salió bien y qué no al cerrar un trabajo. Alimentan a /improve-skills.
gh y jq
gh es la CLI oficial de GitHub; jq procesa JSON desde la terminal.
Subagente
Un agente lanzado por otro para una tarea acotada, con su propio modelo y contexto.
Worktree
Una copia de trabajo extra del mismo repo git, para que cada agente trabaje en su rama sin pisar a los demás.
