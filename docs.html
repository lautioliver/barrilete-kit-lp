Documentation

All of barrilete-kit on one page.

A repo template for working with coding agents without losing control: clear rules, tested documentation and an issue-to-PR flow where people approve the plan and merge.

The template installs in English by default: rules, skills, docs and GitHub conventions, and commit and PR descriptions go in English. With --lang es everything is installed in Spanish instead, including the commit rule. Labels, file names and script messages are in English in both.
  • Rules for agents. AGENTS.md says what an agent can do on its own, what it must ask about first and what it must never do.
  • Skills for the whole cycle. Plan, open issues, implement with TDD, review PRs, debug and migrate the database.
  • Docs as infrastructure. CI checks links, paths and ADRs, and flags which docs to review based on what changed.
  • Gets better with use. Every run leaves a retro, and skill changes always arrive as a PR.

Get started

Trying it for the first time to tell us how it went? Follow the test guide: steps, what to note and the form to report it.
You need an authenticated gh (gh auth status), jq and python3. See Requirements.
  1. On GitHub: Use this template → Create a new repository, then clone the new repo.
  2. Initialize it:
    bash
    ./scripts/init-template.sh "Project name" main

    It fills in the name, base branch, branch rule and date across every file, writes .agent-kit.json (commit it) and deletes itself. To pick another base branch or the small mode, see Modes.

  3. Fill in the TODO: markers (grep -rn "TODO:" .). At minimum:
    • AGENTS.md: what it is, stack, commands and code conventions.
    • docs/agents-map.json: the real paths for schema, auth, payments and public API, plus the verify commands.
    • .github/labels.yml and .github/labeler.yml: the area: labels and your repo's paths.
    • docs/github-naming-convention.md §2: commit scopes.
  4. Load the team: /add-member @user for each member, with the areas they cover. From then on, every issue the agents create is born assigned (see Team and assignment).
  5. Create the labels: Actions → Labels → Run workflow.
  6. Using Codex? Link the skills: mkdir -p .agents && ln -s ../.claude/skills .agents/skills. Copilot and Cursor read them from .claude/skills as is. See Tools.
The docs check fails on purpose while docs/agents-map.json still has TODO/ paths: with example paths, an agent would never notice it touched something sensitive. Paths starting with ? are optional stack alternatives; your own paths go without ?, so the check fails if they stop existing.

Add to an existing project

Already have a repo? The installer adds the kit without overwriting your files. Run it from the root of the project, with a clean working tree:

bash
curl -fsSL https://raw.githubusercontent.com/lautioliver/barrilete-kit/main/scripts/install.py | python3 - "Project" main [--lang es] [--small] [--draft]

Or clone the template and run it from the clone, to read it before running it:

bash
python3 <clone of the template>/scripts/install.py "Project" main

main is the base branch (or develop), and releases works as in the init. --draft prints the plan and writes nothing. --template <url or path> and --version vX.Y.Z pick where the kit comes from. Anything after -- goes to init-template.sh as is (for example -- --lang es).

Review it before you commit anything. The installer doesn't commit: review git status and the diff. Then:

  1. Integrate what is worth keeping from .agent-kit/pending/ into your files and delete that folder: update.py won't run while it has files. If .agent-kit/pending/.github/labels.yml is there, merge its labels into your .github/labels.yml before the first sync.
  2. If the project already had .github/labels.yml, the Labels workflow (.github/workflows/labels.yml) stays in .agent-kit/pending/ and is withheld: update.py and grow.py won't bring it back. Once your labels.yml has the repo's labels, install it yourself by copying .agent-kit/pending/.github/workflows/labels.yml to .github/workflows/labels.yml. The next update.py run removes it from withheld in .agent-kit.json. Until then there is no label sync, so don't delete the folder before doing this.
  3. If .claude/settings.json is in .agent-kit/pending/, the guardrails hook is not active until you integrate it. Otherwise it is already active.
  4. Right before merging the PR, run the labels command the installer prints, and commit the result: the PR can take days, and the first sync deletes any label created in the meantime that is not in the file.
bash
gh label list --limit 1000 --json name,color,description | python3 scripts/agents/labels.py .github/labels.yml > /tmp/labels.yml && mv /tmp/labels.yml .github/labels.yml

To have an agent do the integration in the same PR, ask it something like this:

Integrate what is worth keeping from .agent-kit/pending/ into my files (AGENTS.md, docs, PR template), keep the guardrails hook active in .claude/settings.json, delete the folder, and do it in this PR.

The flow

  1. Idea.
  2. /plan-feature builds the epic and its issues.
  3. You approve the plan.
  4. /implement-issue <n>: red tests, proven with a JUnit or TAP report (see Verified red), then code until green, and the PR.
  5. /review-pr <n> reviews it from another session and re-runs the red.
  6. You merge.
  7. The retro feeds /improve-skills, which proposes skill changes in a PR.

Agents do the work. The two knots on the leash, approving the plan and merging 🟡, always stay in human hands.

Guardrails. It doesn't rely only on what AGENTS.md asks: a Claude Code hook (.claude/settings.json → scripts/agents/guardrails.py) stops, before they run, merging and approving PRs, pushing to main or develop, tags, releases, branch protection changes and --no-verify, also inside compound commands. The same script is registered for Codex, Copilot and Cursor (see Tools). If you asked for one of those steps, run it yourself in the chat: ! gh pr merge 12. Open Claude Code at the repo root: from a subdirectory it doesn't load .claude/settings.json and the hook doesn't run. They are guardrails, not a lock: they stop the common mistake, but an agent with your token can get there another way (its own script, another tool). The lock is GitHub: a rule on the base branch that requires an approval. If you work alone, that rule also stops you (GitHub doesn't let you approve your own PR), so it's optional.

During /implement-issue, debug, db-migration and update-docs come in as needed. If the PR touches sensitive paths, the review adds /security-review.

Verified red

TDD only helps if the red is real. red.sh doesn’t guess from the runner’s output: it reads a structured report (JUnit XML or TAP) and fails closed (ADR-002). A red counts only when all of this holds:

  • the command exits with an error, and the report was created in this run;
  • at least one case ran, and at least one failed on an assertion;
  • there are no errors, crashes, signals or timeouts (600 s by default);
  • every failing case is a test that the red commit adds or changes. An old broken test proves nothing.

Each stack declares its command in the red section of docs/agents-map.json: a name, the test files it covers (when), the command with {out} where the report goes, and the format. The per-runner guide has entries ready to copy for pytest, vitest, jest, go, cargo and bash.

The PR carries the red commit and its failing cases, and the labels check requires that block. The reviewer re-runs red.sh from its own trusted checkout at that commit and compares the cases. A PR that changes the red section needs a person’s approval.

Skills

They live in .claude/skills/.

SkillWhat for
/plan-featureResearches code, architecture and ADRs, writes a technical plan and turns it into an epic + issues. Writes no code.
create-issueStandalone issues, audit → issues, blockers between existing issues.
/implement-issue <n>From issue to PR with TDD: red tests from the acceptance criteria (red.sh checks they fail on an assertion), code until green, self-review, docs and PR. Never merges.
debugSymptom → evidence → root cause → fix → regression test.
db-migrationA plan with compatibility, backfill and rollback before touching the schema.
update-docsFinds docs a change made stale (using the map) and fixes them in the same PR.
/review-pr <n>A review focused on what's specific to the project: business rules, ADRs, autonomy, docs, tests and sensitive paths. Never approves.
/project-statusAn on-the-spot summary (version, work, epics, PRs, debt, decisions, migrations) and "what can I work on now?".
/orchestrateSplits up to 3 available issues among subagents working in parallel (Haiku or Sonnet per routing.py, Opus reviews), each in its own worktree, and gathers PRs, questions and escalations in a single message. Never merges or posts without confirmation.

Subagents by model

In .claude/agents/, each role with its model:

SubagentModelWhat for
implementerSonnetimplement-issue in the worktree it is given: business logic, bugs, features and whatever the light one escalates.
implementer-lightHaikuSmall issues without sensitive paths or business logic. If it runs into any of that, it stops and escalates.
reviewerOpusreview-pr from another context, in its own worktree. It does not publish: it returns the findings.

/orchestrate launches them from the main session. They share the rules and the output format of docs/agents/subagent-contract.md, and each one works in its own worktree (prepare.sh <n> --worktree). check-docs.py checks that each one has a model, tools and the contract.

How they learn

Skills get better with use, but they never rewrite themselves.
  1. Every implement-issue and review-pr run leaves a retro on the agents/retros branch. It's plain git: it doesn't clutter PRs or depend on GitHub.
  2. /improve-skills looks for patterns (at least two cases, or one serious one) and prefers turning them into scripts or checks over adding more text. It always proposes through a PR, and can be scheduled to run weekly.
  3. Whatever is useful but not enough to change a skill goes to docs/agents/lessons.md, which implement-issue reads before starting. Agents learn from consolidated, reviewed lessons, never from raw retros.

Skills are capped at 120 lines, enforced by check-docs.py. Two checks in the labels workflow came out of this loop on a real repo: a PR labeled business-logic must touch docs/decisions/ (or say ADR sin cambios: <motivo>), and a PR that arrives without a type: label copies it from the issue it closes.

Team and assignment

.github/team.json lists the members (GitHub user, name, the area: labels they cover, active or paused). Only the scripts that create issues read it: create-issue and planner.py (epics). Each new issue is assigned like this:

  1. Among active members, those who cover one of the issue's area: labels.
  2. If nobody covers it (or the issue has no area), all active members.
  3. The one with the fewest open assigned issues wins; in an epic, the load is also spread across the issues of the same plan. Tie: the first one in the file.

With no members, issues stay unassigned. The team is changed with /add-member and /remove-member (scripts/agents/team.py), which check that the user exists and has access to the repo; check-docs.py checks that the areas still exist in labels.yml.

Assigned means owner, not "working on it": available.sh shows your issues first, treats as "in progress" what has an open PR, and separates what was merged to develop but awaits a release. prepare.sh won't let you take an issue owned by someone else.

Modes

Base branch

The init's second argument sets where PRs go:

CommandFlowWhen
init-template.sh "X" mainbranch → main🌱 New project, no users yet
init-template.sh "X" developbranch → develop → main🔀 Keep integration apart from production
init-template.sh "X" develop releasesbranch → develop → release/vX.Y.Z → main🚢 Live users: each version is frozen and tested on staging before reaching production

Full or small

For one- or two-person projects, add --small: ./scripts/init-template.sh "X" main --small.

The prose language is chosen with --lang en|es (default en; it combines with --small and releases): with es, each X.md is replaced by its X.es.md sibling; either way the leftover .es.md files are deleted, and language is recorded in .agent-kit.json so update.py and grow.py reproduce the install. In the template, with "parity": true in docs/agents-map.json (the init leaves it false in projects), check-docs.py requires every X.md to have its X.es.md with the same headings and code blocks.

🦅 Full🐣 --small
Skills136: implement-issue, create-issue, debug, update-docs, add-member, remove-member
Workflows42: docs and label sync
Labelstype:, area:, priority:, status: and specials7: type: and priority:

The small mode keeps only the README in the chosen language (English by default; --lang es keeps the Spanish one).

When the small project grows

python3 scripts/grow.py moves it to full mode (add --releases if the base is develop and you want that flow). It clones the template, initializes it with the data in .agent-kit.json and adds what's missing:

  • Files the project never touched are replaced with the full version.
  • Files it modified are not overwritten: the full version lands in .agent-kit/pending/ for you to merge in.
  • The small project's architecture moves to docs/development/architecture.md.

It doesn't commit: you review the diff and open a PR.

Small-mode files live in profiles/small/ (plus the DELETE list). What both modes share (skills like debug, check-docs.py, prepare.sh) is the same file, so fixes reach both.

Updating

The template has versions (vX.Y.Z tags, changes in CHANGELOG.md), and init records in .agent-kit.json which one the project was created from. To bring in the latest:

bash
python3 scripts/update.py                    # or --version v1.2.0

It initializes the new version with the project's data and compares it file by file against the original version:

  • Files the project never touched are replaced, new ones are added and files the template removed are deleted.
  • Files both sides changed are merged with git merge-file. On a conflict nothing is overwritten: the merge with markers lands in .agent-kit/pending/.
  • Files the project deleted don't come back.

It shows what changed according to the changelog and doesn't commit: you review the diff and open a PR. A project created before versions can also be updated, but without merging: what it modified lands whole in .agent-kit/pending/.

Trying it in another tool
  1. Rules: ask it "what can't you do without asking?". It should quote the Autonomy section of AGENTS.md.
  2. Skills: ask it to "follow the implement-issue skill for issue N" (or /implement-issue N if it recognizes it). It should take the issue with prepare.sh, commit the red tests with red.sh and open the PR without merging it.
  3. Guardrails: ask it to run gh pr merge 999999. The hook should stop it before it runs.
  4. If something fails, open an issue with the tool, its version, the step and the exact error. That moves the table from 📄 to ✅ or ❌.

Requirements

  • An authenticated gh, jq and python3 on the machine where the agent runs.
  • Sub-issues and issue dependencies ("Blocked by" / "Blocking") enabled on GitHub. Without them, skills report the error (404/422) and write the blocker into the issue body, but planner.py, available.sh, prepare.sh and unblock.yml lose the automatic part.
  • Agents must be able to push to the agents/retros branch. If you protect branches with a broad pattern (*), exclude it. If they can't push, retro.sh keeps retros in .git/pending-retros/.
