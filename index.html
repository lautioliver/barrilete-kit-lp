The thesis

Two decisions are always yours.

Checkpoint 1

Approve the plan.

/plan-feature researches the code and the ADRs, builds the epic with its issues and blockers, and shows it to you. It writes no code until you say yes.

Checkpoint 2

Merge.

/implement-issue goes all the way to a PR with green tests. /review-pr reviews it in another session. A person does the merge.

Skills get better with use, but they never rewrite themselves: /improve-skills proposes changes in a PR and never loosens controls.

The flow

From idea to merge, with the leash tied at two knots.

Guardrails

.claude/settings.json + guardrails.py: a hook that stops merges, tags, releases and pushes to trunk branches.

Agent map

docs/agents-map.json says which docs to review based on what changes and which paths are sensitive.

Docs tested in CI

Broken links, paths and ADRs, map paths that no longer exist, shellcheck and the test-*.sh: if something breaks, the check fails.

Verification before the PR

verify.py runs lint, typecheck, affected tests and migration drift based on what changed.

Verified red

red.sh accepts a red only from a JUnit or TAP report: an assertion that fails in a new test. Crashes, timeouts, load errors and old broken tests don’t count.

Issues from the chat

Just ask in the chat

You say one sentence. This happens.

“open an issue: the QR code doesn’t validate offline, it’s urgent”
→ create-issue

Writes the title and labels following the convention, looks for duplicates, shows you the draft and creates it once you confirm.

“the payments migration depends on issue 25 being closed”
→ create-issue

Records GitHub’s native dependency (“Blocked by”) and adds status:blocked. unblock.yml removes it once every blocker is closed.

“plan the accounts migration”
→ /plan-feature

Researches the code and builds an epic with sub-issues and blockers, in the order they can be done.

“turn this audit into issues”
→ create-issue

One issue per finding, linking back to the document.

“what can I work on now?”
→ /project-status

What’s free by priority, what’s blocked and why, and the progress of each epic.

“add @ana to the team, she covers payments”
→ /add-member

Checks the user and the areas and adds them to .github/team.json. Payments issues are born assigned to whoever has the least load.

Skills

13 skills for the whole cycle.

They live in .claude/skills/. The ones starting with / are invoked as a command; the agent uses the others when needed. Capped at 120 lines each, enforced by check-docs.py.

/plan-feature
Researches and turns an idea into an epic + issues. Writes no code.
create-issue
Standalone issues, audits into issues, blockers between issues.
/implement-issue <n>
From issue to PR with TDD: red.sh checks the tests fail on an assertion, then code until green. Never merges.
debug
Symptom → evidence → root cause → fix → regression test.
db-migration
A plan with compatibility, backfill and rollback before touching the schema.
update-docs
Fixes the docs a change made stale, in the same PR.
/review-pr <n>
Reviews business rules, ADRs, docs, tests and sensitive paths. Never approves.
/improve-skills
Gathers retros and objective signals (CI failures, reverts) and proposes skill changes in a PR. Never loosens controls.
/project-status
Version, work, epics, PRs, debt, decisions and “what can I work on now?”.
git-workflow
Branches, commits and PRs.
/orchestrate
Splits up to 3 issues among subagents working in parallel, each in its own worktree, and gathers PRs and questions in a single message.
/add-member · /remove-member
Add, edit, pause or remove the team members who receive issues.
Subagents by model

Three in parallel. None of them merges.

/orchestrate splits up to 3 available issues: it picks Haiku or Sonnet per routing.py and Opus reviews. Each one works in its own worktree and all share the contract in docs/agents/subagent-contract.md.

Sonnet
implementer

implement-issue in the worktree it is given: business logic, bugs, features and whatever the light one escalates.

Haiku
implementer-light

Small issues without sensitive paths or business logic. If it runs into any of that, it stops and escalates.

Opus
reviewer

review-pr from another context, in its own worktree. It does not publish: it returns the findings.

Ready PRs, questions and escalations arrive together in a single message. Nothing is merged or posted without your confirmation.

How they learn

They get better with use. They never rewrite themselves.

  1. 1
    A retro on every run

    Every implement-issue and review-pr run leaves a retro on the agents/retros branch. Plain git: it doesn’t clutter PRs.

  2. 2
    Patterns, not anecdotes

    /improve-skills looks for at least two cases (or one serious one) and prefers turning them into scripts or checks over adding more text. It can be scheduled weekly.

  3. 3
    Always in a PR

    Changes arrive as a PR. Whatever isn’t enough to change a skill goes to docs/agents/lessons.md, which implement-issue reads before starting.

Agents learn from consolidated, reviewed lessons, never from raw retros. Two checks in the labels workflow came out of this loop on a real repo: a PR labeled business-logic must touch docs/decisions/, and a PR that arrives without a type: label copies it from the issue it closes.

Team and assignment

Every issue is born with an owner.

.github/team.json lists the members: GitHub user, name, the areas they cover, active or paused. Only the scripts that create issues read it: create-issue and planner.py.

01
By area

Among active members, those who cover one of the issue’s area: labels.

02
If nobody covers it

All active members.

03
Least load wins

The one with the fewest open assigned issues. In an epic, the load is also spread across the issues of the same plan.

Assigned means owner.

Not “working on it”. available.sh shows your issues first, treats as “in progress” what has an open PR, and separates what was merged but awaits a release. prepare.sh won’t let you take an issue owned by someone else.

For teams.

--small

For one or two people.

Base branch

The init’s second argument sets where PRs go.

init-template.sh "X" main
branch → main

New project, no users yet.

init-template.sh "X" develop
branch → develop → main

Keep integration apart from production.

init-template.sh "X" develop releases
branch → develop → release/vX.Y.Z → main

Live users: each version is frozen and tested on staging.

Did the project grow? python3 scripts/grow.py moves it to full mode (add --releases if the base is develop and you want that flow). Files you never touched are replaced; files you modified stay intact and the full version waits in .agent-kit/pending/. It doesn’t commit: you review the diff and open a PR.

Add to an existing project

Already have a repo? The installer adds the kit without overwriting your files. Run it from the root of the project, with a clean working tree:

bash 
curl -fsSL https://raw.githubusercontent.com/lautioliver/barrilete-kit/main/scripts/install.py | python3 - "Project" main

Or clone the template and run it from the clone, to read it before running it:

bash 
git clone https://github.com/lautioliver/barrilete-kit /tmp/barrilete-kit
python3 /tmp/barrilete-kit/scripts/install.py "Project" main

Options: --lang es writes the prose in Spanish, --small is the small mode and --draft prints the plan and writes nothing. main is the base branch (or develop), and releases works as in the init. --template <url or path> and --version vX.Y.Z pick where the kit comes from. Anything after -- goes to init-template.sh as is (for example -- --lang es).

What it touches
README, LICENSE
Doesn’t touch them
.gitignore
Adds what is missing in a # barrilete block
CLAUDE.md
If it doesn’t import @AGENTS.md, adds the line
.claude/settings.json
JSON merge: adds the guardrails hook to your hooks. If the file is not valid JSON, has no hooks object or is a symlink, the kit’s version goes to .agent-kit/pending/ instead
Workflow with the same name
The kit’s is installed as barrilete-<name>.yml
.github/labels.yml
The kit’s labels plus the ones the repo had at install time (gh label list), so the first sync deletes none of them
Any other file you already have (for example AGENTS.md, docs/README.md, the PR template)
Keeps yours; the kit’s version goes to .agent-kit/pending/

Review it before you commit anything. The installer doesn’t commit: review git status and the diff, integrate what is worth keeping from .agent-kit/pending/ and delete that folder. The full steps (labels, the Labels workflow, the guardrails hook) are in the documentation.

The template installs in English by default: rules, skills, docs and GitHub conventions, and commit and PR descriptions go in English. With --lang es everything is installed in Spanish instead, including the commit rule. Labels, file names and script messages are in English in both.
Glossary

The onboard dictionary.

The technical words on this page, one line each.

Coding agent
An AI model (Claude Code, Cursor) that reads, writes and runs code in your repo.
Repo template
A GitHub repo you copy as the starting point for a new one, with all its files.
AGENTS.md
The file with the rules the agent reads before working. CLAUDE.md and llms.txt point to it.
Skill
A written recipe the agent follows for a specific task. The ones starting with / are invoked as a command.
ADR
Architecture Decision Record: a short document recording a technical decision, why it was made and what was discarded.
Issue
A task, bug or request recorded on GitHub, with its acceptance criteria.
Epic
A large issue that groups several sub-issues of the same feature.
Blocker
A dependency between issues: one cannot start until the other is closed.
PR
Pull request: the request to bring a branch’s changes into the main one, where they get reviewed.
Merge
Accepting a PR and integrating its changes into the main branch.
Label
A tag on issues and PRs (type:, status:…) to classify and filter them.
CI
Continuous integration: automatic checks that run on every PR and fail if something broke.
Workflow
A GitHub Actions file (.yml) that automates something: running tests, syncing labels, unblocking issues.
TDD
Test-driven development: first you write the failing test (red), then the code that makes it pass (green).
JUnit and TAP
Two standard formats in which test runners report the result of each case. red.sh reads them instead of guessing from the output.
Lint and typecheck
Automatic style and type checks that find errors without running the code.
Regression test
A test that reproduces an already-fixed bug, so it never comes back.
Migration and schema
The schema is the structure of the database; a migration is the versioned change that modifies it.
Backfill and rollback
Backfill: filling in existing data after a schema change. Rollback: the way to undo it.
Sensitive paths
Parts of the code where a mistake is costly (auth, payments, schema, public API) and that get extra review.
Retro
Notes on what went well and what didn’t when closing a piece of work. They feed /improve-skills.
gh and jq
gh is GitHub’s official CLI; jq processes JSON from the terminal.
Subagent
An agent launched by another for a bounded task, with its own model and context.
Worktree
An extra working copy of the same git repo, so each agent works on its own branch without stepping on the others.
